# Публикация Tune Arena через Cloudflare Builds

GitHub хранит исходники. Установку зависимостей, сборку и публикацию выполняет Cloudflare Workers Builds. GitHub Actions для этого процесса не нужен.

## Две ошибки со скриншотов

- `Could not detect a directory containing static files`: выполнялся `npx wrangler deploy` из корня без сборки web-приложения.
- `Set Cloudflare build variables`: прежний скрипт требовал UUID D1, имя R2 и адрес сайта ещё до компиляции. Теперь компиляция проходит без этих значений. При публикации настройки можно получить автоматически через API Cloudflare.

## Настройки существующего Worker

Открыть **Workers & Pages → нужный Worker → Settings → Build**. Адрес `/ai/models/...` относится к каталогу AI, а не настройкам сайта.

| Поле | Значение |
|---|---|
| Production branch | `main` |
| Root directory | `/` (корень репозитория) |
| Build command | `npm run build:cloudflare` |
| Deploy command | `npm run deploy:cloudflare` |
| Node.js | `24` (включён `.node-version`) |

Сохранить команды и запустить последнюю версию `main`. Для публикации используются production-данные; непроизводственным веткам нужны отдельные ресурсы и адрес.

## Автоматическая настройка D1/R2

Команда публикации использует `CLOUDFLARE_API_TOKEN` и `CLOUDFLARE_ACCOUNT_ID` в среде **Cloudflare Builds**. Выбранный в **Settings → Build → API token** токен должен иметь права на Workers Scripts, D1 и Workers R2 Storage (Edit/Write). Если ID аккаунта не передаётся средой сборки, добавить `CLOUDFLARE_ACCOUNT_ID` в **Build Variables and Secrets**. Значение — ID выбранного аккаунта Cloudflare, не ID базы D1. Токен не передавать в переписке и не сохранять в исходниках.

Во время публикации скрипт:

1. Читает привязки `DB` и `BUCKET` существующего Worker и сохраняет их. Сохраняет существующий HTTPS-origin и Telegram ID владельцев, если они не заданы явно.
2. Если привязок нет, находит D1 с именем Worker или создаёт её. Аналогично использует либо создаёт R2 bucket `<имя-Worker>-photos`.
3. Если адрес сайта ещё не указан, получает зарегистрированный поддомен workers.dev и формирует HTTPS-origin Worker. Для своего домена задать `TUNE_APP_ORIGIN` явно.
4. Готовит production-конфигурацию, применяет миграции D1 и только затем публикует Worker.

Имя Worker берётся из `WRANGLER_CI_OVERRIDE_NAME`, который Cloudflare передаёт своему Wrangler, затем из `TUNE_WORKER_NAME`, по умолчанию `tune-arena`. Если ранее ресурсы были созданы под другими именами, указать их вручную либо привязать к существующему Worker перед запуском.

Повторный запуск находит созданные ресурсы. Данные не удаляются, базы не пересоздаются, случайное переключение имеющихся привязок блокируется. При ошибке токена, доступа, ответа API или миграции публикация останавливается. Если D1 создана, а создание R2 не прошло, D1 остаётся и используется при повторе; автоматического удаления нет. При одновременных первых запусках возможна ошибка конфликта создания — повтор использует уже созданный ресурс.

При отсутствии workers.dev-поддомена нужно включить его в Cloudflare либо указать существующий HTTPS-origin. R2 должен быть включён в аккаунте; скрипт не меняет подписки, биллинг и платёжные данные.

## Ручные значения остаются поддержаны

При указании всех трёх значений API-настройка ресурсов не запускается:

| Build variable | Значение |
|---|---|
| `TUNE_D1_DATABASE_ID` | реальный UUID существующей D1 |
| `TUNE_R2_BUCKET_NAME` | точное имя существующего R2 bucket |
| `TUNE_APP_ORIGIN` | HTTPS-origin сайта без пути, query и пароля |

Дополнительно поддерживаются `TUNE_WORKER_NAME`, `TUNE_D1_DATABASE_NAME`, `TUNE_R2_JURISDICTION`, `TUNE_ADMIN_TELEGRAM_IDS` (числовые ID владельцев через запятую). Локальный preview UUID запрещён для публикации. При отсутствии ID владельцев администраторы не назначаются по никнейму или GitHub-доступу.

## Telegram

После публикации задать `TELEGRAM_BOT_TOKEN` как **Worker runtime secret**. Для browser OIDC отдельно нужны `TELEGRAM_CLIENT_ID` и `TELEGRAM_CLIENT_SECRET`. Связать HTTPS-адрес с ботом и проверить Mini App согласно [TELEGRAM_MINI_APP_RU.md](TELEGRAM_MINI_APP_RU.md).

## Проверка

```sh
npm run build:cloudflare
```

Команда компилирует SSR/API и клиент, не требует ресурсных переменных и не обращается к Cloudflare API. Если все ручные параметры заданы, она также готовит production-конфигурацию.

```sh
npm run deploy:cloudflare -- --dry-run
```

Dry-run требует все три ручных параметра, проверяет упаковку без создания ресурсов, remote-миграций и публикации. Настоящая команда `npm run deploy:cloudflare` получает ресурсы автоматически либо использует ручные значения, затем применяет миграции и публикует.

Локальные API-тесты используют имитированный Cloudflare и проверяют создание, повтор, пагинацию, сохранение данных и владельцев, отказы доступа и отсутствие токенов в выводе. Это не подтверждение реальной публикации. Её подтверждают успешный Cloudflare deployment и проверка адреса сайта.
